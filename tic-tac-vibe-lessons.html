Tic-Tac-Vibe: Firebase Realtime Quirks and Endless Loops

I decided to modernize Tic-Tac-Toe. Instead of just static 3x3 play, I wanted to build an "endless" multiplayer version where pieces automatically vanish from the board after 5 turns. I called it Tic-Tac-Vibe. The goal was to build the entire multiplayer architecture within a single index.html file using Firebase Realtime Database via CDN imports.

The Endless Loop Mechanic

Tracking the endless state was a fun data modeling challenge. Instead of simply storing an 'X' or 'O' in a board array, I had to track the timestamp/turn-number of each move. I set an internal constant MOVES_BEFORE_DISAPPEAR = 5. Every time a player makes a move, the local state loops over the board, identifies any piece where nextMoveNumber - piece.moveNumber >= 5, and flags it as null. This immediately forces the oldest plays to dissolve, keeping the game in a constant flow state.

The Sparse Array Bug from Hell

The most devastating bug hit during multiplayer synchronization. Firebase Realtime DB optimizes JSON trees automatically over the wire. If you save an array like ['X', null, null, 'O'], Firebase will drop the null elements to save data, effectively transforming it into a sparse object dictionary: {0: 'X', 3: 'O'}.

When my onValue listener grabbed the game board data and stuffed it back into the local UI rendering loop, it expected a 9-item dense array. Instead, it received a fragmented object which completely crashed my board-filling loops and win condition checks.

I had to explicitly engineer a dense array parser inside the updateBoard(boardData) function to loop through 0-8 linearly, using hasOwnProperty to map the sparse keys back into a guaranteed rigid 9-item array before rendering the React-style state updates. It was an incredibly frustrating nuance of Firebase, but solving it enabled seamless, bug-free multiplayer gameplay directly hosted on a static URL.
